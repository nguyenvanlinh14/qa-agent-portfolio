## Bản cho k6 (`k6-3062-test-install.yml`)

Giống prototype, thêm: trigger `workflow_run` sau workflow `Build` cho tag `vX.Y.Z` mới nhất (bỏ qua pre-release / bản major cũ), retry tối đa 6 lần × 5 phút cho kênh first-party (apt, dnf, MSI, Docker) vì dl.k6.io cần thời gian lan truyền; Homebrew/winget chỉ chạy theo lịch và báo **warning** khi trễ. Không dùng action bên thứ ba; `${{ }}` đi qua `env:` (zizmor).

> I prototyped the workflow outside k6 first so it could be validated on real runners: https://github.com/nguyenvanlinh14/qa-agent-portfolio/actions/runs/40499430856 — it installs k6 the documented way and asserts `k6 version` matches the latest release on:
> - Docker containers (on `ubuntu-latest`): ubuntu:22.04, ubuntu:24.04, debian:12 (apt + `dl.k6.io/key.gpg`), fedora:latest, rockylinux:9, amazonlinux:2023 (dnf + `repo.rpm`)
> - macOS: Homebrew; Windows: MSI (`k6-latest-amd64.msi`) and winget
> - `grafana/k6:<version>` image
>
> It already caught one thing: **winget installs v2.2.0 while v2.3.0 is the latest release**, so the winget manifest seems to lag behind.
>
> For k6 itself I'd add it as `.github/workflows/test-install.yml`, triggered daily, on `workflow_dispatch`, and via `workflow_run` after `Build` for a new latest-stable tag (with a bounded retry while dl.k6.io propagates). Homebrew/winget would only run on the schedule and warn instead of fail when they lag.
