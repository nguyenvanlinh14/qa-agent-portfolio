Case study · AI-agent QA workflow

The agent does the legwork. I keep the decisions.

Multi-tenant B2B SaaS for Japanese stock screening (client names withheld)

Team
One QC (me) and Claude Code, working in the QA repository
Environments
DEV → TEST (pre-production) → PROD
Roles tested
Super Admin; per tenant Owner, Moderator, Member

Problem

In one sprint my API-level regression stayed green while the UI showed an error toast after a successful delete. The API was right, but the user still saw a failure.

The second problem was the release itself. Checks were manual and the evidence was scattered, so it was hard to prove afterwards what had been checked and where.

The product multiplies the effort. Each client tenant has its own branded user site (ranking, stock analysis, watchlist, dashboard, backtest, alerts, AI chat) next to a shared admin site (members, packages, screening rules, notifications, datasets for the AI chat, audit log). Features depend on the member package, for example Essential or Premium, and the TEST environment is pre-production but used by real customers.

Approach

The agent works as an end user, as a QC and as a QA-automation engineer. I keep every decision that carries risk. Everything the agent produces is backed by evidence: a screenshot with the page URL and the environment, or a video for bugs.

I decide

  • Approving test cases
  • Go / No-go for a release
  • Any data change on PROD
  • Any conflict between a requirement and the current system

The agent does

  • Walks the product role by role
  • Maps scope and asks when it is unclear
  • Writes cases and automation, runs and triages them
  • Collects evidence and reports facts

Workflow A · Build the test suite for a feature

#WhoStep
1QCI create a secured .env per environment and tenant with the test accounts of every role (git-ignored, owner-only file permissions) and declare the guardrails: forbidden environment and tenant pairs, which accounts may change data, and whether PROD may be changed.
2AgentWalks through the product as an end user, role by role, with the .env accounts. The result is a map of screens, flows and current behaviour with screenshots (“as is”, not yet “correct”).
3QCI add the requirements: client request, prototype and tickets.
4AgentMaps the impact scope (which screens, roles and packages are affected or not) and asks me about anything unclear. No test case is written while the scope is unclear.
5AgentWrites the test cases per feature as a QC. Each case is tagged with its source: requirement, then prototype, then current system. A conflict between sources becomes a question, never a silent choice.
6–8QC + AgentI review, the agent updates, and I review again until the suite is approved.
9AgentWrites the automation as a QA-automation engineer. It runs the scripts against the real environment until they are stable, separates script errors from product errors, restores and re-verifies every data change, tags the scripts and registers them in the coverage map.
10QCI review the scripts and loop until they are accepted.

Workflow B · Run a feature in each test cycle

#WhoStep
1AgentWalks through the feature as an end user.
2AgentCompares the walkthrough with the test suite before running it: new UI, changed labels, changed flows.
3AgentFixes small changes (selector, label) in the script and notes them. Big changes go to me as a question.
4QCI answer: an intended change (update the tests) or a bug.
5AgentRuns and manages the suite: parallelism, sessions, retries, background runs.
6AgentTriages failures. It collapses duplicates into one finding, separates environment failures (expired session, mass 5xx) from product bugs and script bugs, re-runs flaky cases, and checks the bug registry so a known bug is not reported twice.
7AgentFor a new bug, records a video of the reproduction (optionally narrated) and writes a report in the team template: Device, OS, Prerequisite, Account, STEPS, ACTUAL, EXPECT, SCOPE.
8AgentRestores every test change (watchlists, rules, presets, packages, names, notification switches) and verifies it.
9AgentReports as xlsx or HTML, facts only, with evidence on each row.
10QCI review the report.

Workflow C · Production release

#WhoStep
1AgentPulls the release scope from the ticket tracker through its REST API, using my personal API key (kept in a git-ignored file, never printed), and groups the tickets by release item.
2AgentBefore the release, on TEST: one evidence screenshot and check per ticket, plus the full UI regression. Every image carries the URL and an environment label.
3QCI decide Go / No-go.
4AgentAfter the release, UAT on PROD: the same ticket checks and the same regression flows, with test accounts only. All changes are put back and checked.
5AgentUpdates the tickets from the checklist. Passed: comment “Passed on PROD” with a screenshot, then close. Failed or not verifiable on PROD: screenshot only, and the ticket stays open for me.
6QCI handle the open tickets.
7AgentExports the release checklist (xlsx: Summary, Tickets (TEST), Regression (TEST), UAT PROD) with a screenshot in every executed row.

Key techniques

UI smoke regression with a UI guard

One real user flow per feature and role: 69 tests across 2 sites and 6 roles. After every step a guard checks that there is no error text on screen, no API 5xx or unexpected 4xx, and no JavaScript or console error. On failure it takes a screenshot. I introduced it after the sprint where the API-level regression missed the toast error on a successful delete.

Mutate and restore on a shared pre-production tenant

Every flow that writes data restores it in a finally block and asserts the restore. That covers the watchlist, rules (as drafts only), condition presets, datasets, chat threads, scheduled notifications, member packages and the profile name. I never kill a long run midway, because the restore would not run.

  1. Change data
  2. Run the flow
  3. Restore in finally
  4. Assert the restore

Evidence that proves where it was taken

Headless screenshots have no address bar. The agent stamps a browser-style bar on each one with the exact page URL and a label: ENV · tenant · role · time (JST). Red means PROD, blue means TEST.

Tag strategy that keeps maintenance low

  • @regression UI smoke only
  • @deep detailed data comparisons
  • @market-data external market-data checks, such as stock exchange new listings and delistings

All three are selectable in one manual CI workflow.

Coverage map as a CI gate

A JSON coverage map is the source of truth. A sync script regenerates the coverage document from the map and from playwright test --list, and a CI workflow fails any pull request where they drift. Spec files must not read secrets or caches at import time, so the listing works on CI without credentials.

Guardrails enforced by tooling

Instructions alone are not enough. A pre-command hook blocks a forbidden PROD tenant, test data uses only my own test accounts, and risky or outward-facing actions are confirmed with me first.

  • Coverage: 110 tracked sub-features, 90 automated (82%, or 87% including partial), about 1,890 automated test cases.
  • UI regression: grew from 42 to 69 tests (admin site 13 flows, user site 10 flows × roles). New areas: AI chat, datasets, condition presets, draft rules, notifications, audit log, language and theme switch, account settings.
  • Release of 28 Oct 2026: 17 tickets in scope, pulled automatically. TEST: 17/17 tickets passed; regression 53 passed, 16 not applicable, 0 failed. PROD UAT: 46 passed, 4 not applicable.
  • Closed by the agent: 14 tickets were commented with PROD evidence and closed. 3 stayed open with evidence for me: one not verifiable with a Premium test account, one only partly checkable on PROD, and one where maintenance mode cannot be switched on PROD.
  • Run time: a full TEST regression takes about 22 minutes. A PROD UAT run (smoke plus ticket evidence) takes about 15 minutes.
  • Re-verification: all 5 dataset and AI-chat fixes were confirmed, and the agent raised open questions: a duplicate file name re-upload is not skipped, and ingesting about 7.5 MB takes about 15 minutes.

Triage example: 404 on Backtest

Timed reproductions narrowed a “404 on Backtest” bug down to a race. It only happens when the user clicks within about 1 s of switching tabs: 7 of 7 attempts failed when clicking immediately, 0 of 10 failed after a pause of 1–3 s. That finding set the severity correctly.

Lessons

  1. Keep humans on decisions with risk. Approvals, Go / No-go and any change on PROD stay with me.
  2. Demand evidence that shows where it was taken. A screenshot without its URL and environment proves little.
  3. Restore what you change. Shared environments stay trustworthy only if every test puts its data back.
  4. Ask before testing when the scope is unclear. A question costs minutes; a wrong test case costs a cycle.
